# superbench

- Публічний репозиторій містить лише анонімізовані fixtures, benchmark-логіку
  і статичний GitHub Pages; приватний vhost лишається Tailscale-only.
- Не додавати provider API keys або workflow, який запускає сторонній coding
  agent. Candidate запускається окремою сесією Codex або Claude.
- Candidate запускається лише проти `.superbench/workspace/current`; не
  розширювати MCP root на весь репозиторій, бо там є oracle/results.
- Кожну відповідь перевіряють три нові різні reviewer sessions.
- Перед commit: `./scripts/ci.sh`.
- Після зміни даних: `python3 -m superbench render --output site`.
- Nginx static, systemd/backend/database не потрібні.
- Browser runtime повністю локальний: базові токени та шрифти беруться з
  standby-пулу `standby-infra/static` через same-origin `/_/css/superstyle.css`;
  у проєкт не додавати CDN, Google Fonts чи інші WAN-залежності.

## Авторство і співавторство комітів

Issue та PR від імені власника створювати авторизованим акаунтом BenkiNew.
Перед публікацією перевіряти акаунт, після публікації — фактичного автора.
Кожен агент, який підготував зміни, зазначає себе співавтором у повідомленні
коміту окремим трейлером `Co-authored-by: Ім’я <email>`. Використовувати
власне справжнє ім’я агента та офіційну адресу атрибуції його платформи.
Не підставляти іншого агента, вигадану адресу або співавтора без внеску.
Коли зміни підготували кілька агентів, зберігати окремий трейлер кожного.
Під час squash переносити трейлери до кінцевого повідомлення коміту.
Перед push перевіряти трейлери в `git log -1 --format=%B`, після push —
їх збереження в опублікованому коміті. Авторство BenkiNew та співавторство
агентів фіксуються окремо. Чужі наявні коміти не переписувати.

Pull Shark враховує PR авторства BenkiNew зі статусом Merged.
Для Pair Extraordinaire потрібні співавторські коміти у злитих PR,
а зарахування визначає GitHub. Прямий push не створює злитого PR.
Спосіб доставки визначають доручення власника й чинні правила репозиторію.
Не створювати та не дробити PR заради досягнень.
